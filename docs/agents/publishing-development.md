# 发布模块开发规则

开发发布平台、执行流程或恢复逻辑时，先读 [MultiPost 发布技术架构](../multipost-architecture.md)，再阅读本文件。当前实现与真实验收范围见 [发布交接](../research/2026-10-10-publishing-handoff.md)；请求字段、权限和状态协议见 [发布 API](../../packages/publishing-api/README.md)。

## 实现边界

1. 先检查 MultiPost 对应内容类型的平台脚本，沿用其上传、填写和提交流程；在原实现上修复问题。确需替换流程或改变架构时，先说明原因和影响，取得用户确认后实施。
2. 剪藏保持 Vue/WXT 架构，发布保持 MultiPost 的 React、平台脚本和模块组织；通过统一扩展入口集成。根构建只载入显式接入的发布模块，上游 Plasmo 入口仍独立。
3. 图文、视频、文章分别走相应任务 API，再根据平台分发。目标明确选择平台、账号和电脑；浏览器与用户配置可使用预设默认值。用户未明确指定扩展范围时，开发和测试使用 MultiPost 已有平台及其已有内容类型，只覆盖本次任务涉及的组合；新增平台或上游没有的类型须有用户明确指示。API 接入范围与真实验收分别核对。
4. 优先补任务领取、账号核对、参数校验、进度回传、防重复执行、结果确认和故障恢复，不平行新增一套平台发布流程。

## 参数、动作与证据

- Skill 确认后的内容原样执行；超限、缺项或不支持的字段明确报错。合集名称必须精确且唯一匹配；横版和竖版封面分别处理；原创声明同时遵守参数和本次授权。
- 最终动作明确选择填写后保持页面、保存草稿或直接发布。测试优先保存草稿；只有该平台与内容类型确实不支持草稿，且已取得相应发布授权，才测试直接发布。保存失败不升级为发布。
- 平台写操作由 API 驱动扩展；浏览器工具只用于查看和排障。记录平台证据，分别报告 `draft_saved`、`submitted`、`published`、需人工处理、失败或结果未知。异常结果说明已知原因、阶段与下一步；点击成功不等于发布成功。
- 中断后先检查原任务与原页面。仅在旧执行已停止、页面和任务一致时从确定位置接续；不自动重传或重填。提交后的未知结果只核对，不自动重发。

## 验收与文档

逐平台、逐内容类型记录代码检查、构建和真实平台验收。更新相关协议、架构及交接文档，保留历史研究的时间和证据边界。发布规划与决策从 [规划地图](https://github.com/benjamin-qhy/qiushui-clip-publish/issues/17)及相关子议题查阅；代码测试和脚本存在都不等于平台可用。
